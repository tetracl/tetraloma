# M11: Lagrange and DG elements

Design: docs/design.md sections 6, 22 and 26; also 14, 16, 18, 20 (A.5, A.10, A.11) and 23 for the documentation, the tolerances, the crate graph, the oracles and the protected paths
Depends on: none
Milestone issue: created with the task issues, after this plan is merged

## Scope

M11 delivers the Lagrange family of section 26, on the host and in f64.

- **tetraloma-element** (new; the tenth published library crate): Listing E1 for `Family::Lagrange` with the variants `Nodal(Equispaced)`, `Nodal(Gll)` and `Legendre`, on every cell type, in the degree ranges of section 26. This covers `Element::get` and its cache, tabulation, entity DOFs, interpolation points and matrix, base transformations and their classification, and tensor factors on quadrilaterals and hexahedra.
- **tetraloma-refcell:** GLL points on triangles and tetrahedra (Isaac's recursive points) and on prisms; `NodeFamily` becomes `#[non_exhaustive]`; the orthonormal sets and the dense LU become public as `polyset` and `DenseLu`.
- **Oracles:** committed fixtures from ndelement and Basix. Basix joins the pinned Python environment.
- **User documentation:** the API documentation of every public item, and two new book chapters.

Left out:

- N1curl and RT (M12). `Element::get` returns `Unsupported` for them. `Family::N1curl`, `Family::RaviartThomas`, the Piola variants of `MapType`, `TransformationKind::Dense`, `BaseTransformation::Dense` and `Factor1d::MomentH1` are declared as Listing E1 has them, but nothing constructs them.
- Device kernels and element construction on the device (the roadmap entry). `PointSet::tabulate_element` and the dependency of tetraloma-geometry and of the facade on tetraloma-element come with M13 and M14; `GridError::UnsupportedElement` with M14.
- `sub_entity_points_to_cell` (Listing Q1, section 27) is M13's. M11 needs the map onto sub-entities of every dimension for its base transformations, so tetraloma-element keeps a private helper until then.

M11 adds and changes no kernel. So there is no vector-size invariance test, no task has a remote run, and CUDA first sees M11's changes at the gate.

Where a roadmap bullet says "every cell" with a range up to p = 10, pyramids stop at p = 8, the end of their range in section 26 (the roadmap's introduction to M11–M17).

### Where the code differs from the design today

Read from the code on the main branch at 6aac293.

1. **Orthonormal sets.** `tetraloma_refcell::polynomials::tabulate` is crate-private, takes `usize` arguments and returns `[derivative][point][basis]`. Listing E1's `polyset::tabulate` takes `u32` and returns `[derivative][basis][point]`. T3 adds the public function as listed; the private one stays for `LagrangeElement`.
2. **Dense LU.** `Lu::solve(&self, b)` derives the number of right-hand sides from `b.len()`. Listing E1 has `DenseLu::solve(&self, b, nrhs)`. T3 renames the type and adds the argument.
3. **Derivative orders.** tetraloma-refcell tabulates values and first derivatives only and returns `UnsupportedDerivativeOrder` above. Listing E1 gives `nderivs` no range, and its `polyset::tabulate` returns no `Result` (open question 2).
4. **Degree 0.** `lagrange_points` returns `UnsupportedDegree` for degree 0, so no nodal point exists there. Section 26 gives DG the degrees from 0 (open question 1).
5. **Coefficient layout.** `LagrangeElement::coefficients` is `[polyset][basis]`. `Element::coefficients` is `[basis][polyset · value size]`. They are different types in different crates; tetraloma-element follows Listing E1.
6. **`NodeFamily`** is not `#[non_exhaustive]`, and `Gll` is rejected outside intervals, quadrilaterals and hexahedra. Six matches on it outside tetraloma-refcell are exhaustive: in `tetraloma-geometry/src/names.rs`; in `builder.rs`, `pipeline/mod.rs`, `submesh/closure.rs` and `submesh/geometry.rs` of `tetraloma/src/`; and in `tetraloma-bench/src/families/degree.rs`. Tests in four crates and four book chapters state that GLL is unsupported on triangles (T2 lists them).
7. **Basix is not installed.** A.10 calls Basix "pinned in the Python environment", but `scripts/check-local-tools.sh` pins only vtk, meshio and gmsh; Basix's commit is recorded in `sources.json`, and no task has run it. I checked the pin in a scratch environment: `fenics-basix==0.11.0` installs on the local Mac's Python 3.14, offers `gll_isaac` points up to p = 15 on triangles, tetrahedra and prisms, and its pyramid space for p = 1–3 equals the Definition 9 space of A.5 (least-squares residual below 2·10^−13 at 400 points).
8. **ndelement's transformations** are `dof_transformation(entity, Transformation::{Reflection, Rotation})`, returning `Identity`, `Permutation` or `Transformation`. ndelement's `Reflection` of an interval is `Generator::Reversal`. The test of A9 maps the names.
9. **Fixture freshness in CI.** The `conformance` job re-exports the fixtures and compares them byte for byte. Tabulations from ndelement pass through LAPACK, which is Accelerate on the Mac and OpenBLAS in CI, so those files can differ in the last bits (T1).
10. **The documentation audit** lists nine crates in `scripts/check-user-docs.sh`, `scripts/doc_audit.py`, `scripts/build-site.sh` and the `docs` job of `ci.yml`. Sections 14 and 22 say eleven. T4 adds tetraloma-element; tetraloma-function follows in M14.
11. **The book's doctest harness** is tetraloma-examples, which depends on tetraloma, tetraloma-refcell and tetraloma-testing (section 18). A Rust block in the book that calls tetraloma-element would need a dependency that the section 18 row does not list (open question 3).

Carried over from M1b's Deviations log, and still true:

- tetraloma-refcell returns `RefCellError`, which tetraloma-geometry and the facade map to `GridError` (M1b, question 3).
- tetraloma-refcell is built with `opt-level = 3` in the dev profile, because its tests factor Vandermonde matrices of size 729 (M1b, T7). tetraloma-element needs the same.
- The equispaced hexahedron of degree 8 reproduces polynomials to 5.6·10^−13, a margin of about 2 below 10^−12 (M1b, T7). A1, A2, A6 and A10 check equispaced elements only up to p = 6; A11 compares with this dense construction at p = 8 (T7).
- At the pyramid's apex the rational basis functions take their limit along the axis, and their derivatives have no limit over all directions (M1b, T6). No fixture point lies at the apex.
- An ndelement construction in a debug build overflowed a 2 MiB thread stack on Linux (M1b review). The exporter runs on a 64 MiB thread.

## Open questions

1. **Nodal variants at degree 0.** Section 26 gives DG the degrees from 0, but does not say which variants exist there, and no node family has a point at degree 0. Should `Nodal(Equispaced)` and `Nodal(Gll)` at degree 0 be one DOF, the value at the cell's midpoint (the mean of its vertices), with basis function 1 and `discontinuous_only()` true? ndelement and Basix define P0 this way. The alternative is `Unsupported`, which leaves `Legendre` as the only element of degree 0; its basis function is 1/√|K̂|, not 1. I recommend the midpoint element. Needed before T0 (the test of A12 lists the unsupported keys) and T4.
2. **Derivative orders.** Should `nderivs` be 0 or 1 only, as tetraloma-refcell tabulates today? The roadmap bullets of M11–M17 use values and first derivatives only. `Element::tabulate` would return `ElementError::RefCell(UnsupportedDerivativeOrder)` above 1. `polyset::tabulate` returns no `Result` in Listing E1, so it would panic for `nderivs > 1` and for a point array of the wrong length, documented under `# Panics`.
